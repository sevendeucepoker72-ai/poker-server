# Canonical Features Manifest — poker-server (Railway socket server)
#
# PURPOSE: prevent feature regressions on deploy. The deploy script
# (when wired) greps the BUILT bundle (dist/) and/or src/ for every
# non-comment/non-blank line in this file and ABORTS the deploy if any
# are missing. This is the same pattern as the mono-repo apps:
# - apps/web/canonical-features.txt        (player web)
# - apps/web/poker-admin/canonical-features.txt (admin)
# - apps/marketing/canonical-features.txt (marketing)
#
# ENFORCEMENT (2026-08-17): the "Canonical features manifest" step in
# .github/workflows/ci.yml greps the BUILT `dist/` for every token below on
# every push + PR to main, and fails the build on a miss.
#
# Read the previous note as a warning, not history: from 2026-05-12 until
# 2026-08-17 this file claimed to guard against regressions while being
# enforced by NOTHING — no `poker-server` case in the workspace `ship.sh`, no
# deploy script of its own (Railway deploys straight from a git push), and no
# CI step. A lock that nothing checks is worse than no lock, because it makes
# people believe a class of regression is covered.
#
# NOTE ON SCOPE: CI is the enforcement point, NOT the deploy. Railway builds
# from the pushed commit independently, so a red CI run does not physically
# block a deploy the way the FTP/Cloud Run scripts do for the other apps.
# Wiring a Railway pre-deploy check (or a required-status-check branch
# protection rule on main) is the remaining gap.
#
# RULES:
# - One token per line
# - Tokens matched as plain substrings (literal grep -F, not regex)
# - Lines starting with `#` are comments. Blanks ignored.
# - Use string literals (CSS class names, log tags, event-name strings,
#   route paths) that survive Terser minification. Function names get
#   mangled.
# - When you ship a NEW feature you don't want to regress: append the
#   identifying tokens in the SAME commit as the feature.
# - When you legitimately retire a feature: delete the matching tokens
#   in the same commit. The diff is the audit trail.

# 2026-08-17 — .online login observability (SL-3 / LD-2).
#
# poker-server's auth telemetry had NEVER landed a single row
# (`GET /poker-api/auth-events?origin=poker-server` = 0 rows, all time),
# because a missing AUTH_SERVER_BYPASS_KEY made reportAuthEvent a SILENT
# no-op and the POST's outcome was swallowed. That is why a week-long
# ~66%-failure .online sign-in outage was invisible on the Auth Health
# dashboard and why the failing branch could not be identified.
#
# Every loginResult failure branch now carries a machine-readable `code` and
# writes a structured `[login-failure]` line to stdout naming the branch, and
# `authTelemetry` on /api/health reports whether auth events can be delivered
# at all. Losing either is a regression to blind.
#
# 2026-08-17 CORRECTION — these rows are NOT posted as `login_failed`.
# poker-api's alerting computes failure/(success+failure) PER ORIGIN, and
# poker-server never emits a success, so `login_failed` rows from here page
# "poker-server app: 100% fail" forever; worse, its single Railway egress IP
# trips the `isDominated` single-source guard and SILENCES the fleet-wide
# pager. The auth_events POST is therefore opt-in via
# ONLINE_LOGIN_FAILED_EVENT_TYPE (unset = stdout only), and the type named
# there MUST be inside poker-api's CLIENT_EVENT_TYPES allowlist
# (handlers/authEvents.js) — an invented type is 400'd and the row never
# lands, which is how the original blindness went unnoticed for months.
# ============================================================
socket_login
[login-failure]
authTelemetry
ONLINE_LOGIN_FAILED_EVENT_TYPE
no_phone_or_username_claim
user_upsert_failed

# 2026-08-17 P0 — interim account-takeover / admin-escalation guard.
#
# The local users row is keyed ON CONFLICT (LOWER(username)) on auth-server's
# `username` claim, which is `[firstName, lastName].join(' ')` — a NON-UNIQUE
# display name any player can set on themselves (the master API's updateUser
# validates first/last name only as "string, <= 50 chars"). Without the guard,
# renaming yourself to an admin's display name and signing in to .online binds
# you to that admin's row: their chips, their progression, their is_admin.
#
# The guard refuses to bind a login to a row whose stats->>'masterUserId' names
# a DIFFERENT master account, and stamps unowned legacy rows on adoption so they
# become protected on first OIDC login. Deleting any of these tokens re-opens a
# live account-takeover path — restore the code, do not delete the line.
#
# The REAL fix (a master_user_id column + unique index, keyed on the attested
# `sub`) needs a Railway Postgres migration and is still outstanding.
# ============================================================
identity_conflict
masterUserId
#
# 🚨 THE GUARD SHIPS IN WARN MODE and the mode switch is itself load-bearing.
# Enforcing today would permanently lock out 4 KNOWN real humans (production has
# 4 confirmed duplicate master-account pairs sharing a display name) in order to
# close a hole with ZERO measured exposure (no admin display-name collision
# exists across all 2,268 live master accounts). Warn mode runs the identical
# check and logs the identical record, then binds the row exactly as before.
# Losing the mode switch — i.e. hard-coding the refusal back in — is a
